# Stealth Derivation: Current Soroban Proof of Concept

## Status and scope

This document specifies the byte-level behavior implemented by the QuickEx
contract so independent clients can reproduce it. It does **not** certify the
construction as a secure stealth-address protocol. The contract currently
implements a deterministic two-stage SHA-256 construction, not Diffie-Hellman
(DH), Elliptic-Curve Diffie-Hellman (ECDH), or a spendable Stellar account
derivation.

The implementation does not cite a normative stealth-address standard. For
comparison, [EIP-5564](https://eips.ethereum.org/EIPS/eip-5564) describes an
Ethereum stealth-address scheme with elliptic-curve operations. This Soroban
proof of concept is not compatible with or conformant to EIP-5564.

## Exact derivation

Inputs are two byte strings of exactly 32 bytes each:

- `eph_pub`: the value named `eph_pub` in the contract API.
- `spend_pub`: the value named `spend_pub` in the contract API.

They are consumed as raw bytes in the order shown below. There is no text
encoding, length prefix, delimiter, integer conversion, key parsing,
normalization, or curve-point validation. Thus every 32-byte value, including
all-zero and all-`ff` values, is in the accepted input domain.

Using SHA-256 as specified by FIPS 180-4:

```text
shared_secret = SHA-256(eph_pub[0..32] || spend_pub[0..32])
stealth_id    = SHA-256(spend_pub[0..32] || shared_secret[0..32])
```

`||` means byte concatenation. Both hashes are exactly 32 bytes. The API's
`stealth_address` value is this `stealth_id`, returned as 32 raw bytes (commonly
displayed as 64 lowercase hexadecimal digits). It is an escrow lookup
identifier, **not** a Stellar `Address`.

The sender computes these two hashes before calling
`register_ephemeral_key`; the contract recomputes them and rejects a supplied
identifier that differs. The `stealth_withdraw` entry point repeats the
derivation when checking the supplied identifier.

## Deviations and security limitations

- **No DH/ECDH:** `shared_secret` is a hash of two public byte strings. It does
  not use a private ephemeral scalar or a recipient scan private key.
- **No standard-compatible key derivation:** unlike EIP-5564's elliptic-curve
  derivation, this code does not perform curve multiplication/addition and
  cannot derive a spendable Stellar keypair or account.
- **Public inputs:** `spend_pub`, `eph_pub`, and the resulting identifier are
  available to transaction observers. Omitting a key from an event does not
  hide it when it is an invocation argument.
- **No cryptographic ownership proof:** supplying the public values and
  reproducing the hash is not proof of knowledge of a private spend key.
  Withdrawal authorization is the caller's Soroban authorization, not the
  stealth derivation. Since the registration call exposes `spend_pub`,
  `eph_pub`, and the identifier, any observer can reproduce the values needed
  by `stealth_withdraw` and authorize that call with an address they control.
  **This permits third parties to withdraw pending escrow funds; do not rely on
  this proof of concept to protect funds.**
- **Distinct-output test is not a privacy proof:** fixed vectors show that the
  selected distinct ephemeral inputs produce distinct identifiers. That
  inequality alone does not establish cryptographic unlinkability. Because the
  derivation inputs are public, this proof of concept must not be relied on to
  hide payment relationships or prevent third parties from reproducing
  identifiers.

These limitations are deliberate audit findings, not claims that this
proof-of-concept behavior meets a production privacy or key-ownership
requirement.
